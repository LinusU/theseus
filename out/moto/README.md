# Moto Racer (1997) under Theseus

Work in progress: translating Moto Racer, as sold by GOG.com, to run natively
on macOS. GOG ships the July 1998 "Polygons 3.22" patch build (`game.EXE`);
`MotoRacer.exe` in the package is only GOG's launcher. This file is the hand-off document: it records how the pieces fit
together, how to iterate, and what is known to be missing. Update the
**Status** and **Next steps** sections as you go.

## Status

See the bottom of this file ("Log") for the latest state. In short: a full
race plays end to end — menus, track/bike select, racing with keyboard
input, HUD, going off-track, GAME OVER — rendering correctly through the
software renderer at 640x480x16, with the soundtrack playing off the
ripped CD tracks and DirectSound sound effects. Not yet exercised:
multiplayer, joystick, Direct3D.

## Layout

| Path | What |
| --- | --- |
| `moto-racer-input/` | The GOG installer `setup_moto_racer_*.exe` (gitignored). An Inno Setup package; `brew install innoextract` to unpack it. |
| `out/moto/extract.sh` | Unpacks the installer's `app/` directory into `scratch/moto/install/` (gitignored): `game.EXE`, `data/`, the CD audio tracks as `02.wav`..`13.wav`, GOG's `winmm.dll` shim (which we don't use) and `motoracer.ini`. |
| `out/moto/translate.sh` | Runs `tc` on `scratch/moto/install/game.EXE`, writing `out/moto/src/generated*.rs`, `out/moto/data/*.raw` and `out/moto/report.html`. |
| `out/moto/run.sh` | Runs `target/fast/moto` from the install directory with the right environment. Pass game flags through: `out/moto/run.sh -noD3D -noCpuDetect` is the known-good set. |
| `out/moto/moto.reg` | Registry values the installer would have written; the game refuses to start without them (see the comments in the file for the `PId` hash). Loaded through `THESEUS_REGISTRY`. |
| `out/moto/entry-points.txt` | Code addresses tc's scans missed (C++ catch continuations so far), fed back with `--entry-points-file`. Add to it when a run panics with "jmp to unknown addr". |
| `out/moto/src/generated.rs`, `src/generated/part_NN.rs` | Generated by `tc`; do not edit by hand. ~27 MB of Rust for 0xce600 bytes of x86. |
| `win32/winapi/` | The Windows API implementation the generated code calls into. Most work happens here. |

## The loop

```
out/moto/extract.sh                    # once, or when the input changes
out/moto/translate.sh                  # after changing tc, entry-points.txt, or winapi's VTABLES/DYNAMIC_EXPORTS
cargo build --profile fast -p moto     # several minutes when generated code changed, ~1 min otherwise
THESEUS_HEADLESS=1 out/moto/run.sh -noD3D -noCpuDetect   # drop HEADLESS to see the window
```

Run without `-windowed`: windowed DirectDraw needs a clipper
(`IDirectDrawClipper`), which isn't implemented; fullscreen just resizes our
window to the requested mode.

`--profile fast` is opt-level 2 without debug assertions; the plain `dev`
profile is too slow to run the game usefully. Rebuilds after touching only
`win32/winapi` take well under a minute; touching the generated code recompiles
all 40-odd parts.

Useful environment variables (see `host/src/lib.rs`, `win32/winapi/src/trace.rs`):

- `THESEUS_TRACE=kernel32,user32` logs every API call in the named source
  paths with its arguments (substring match on the file path, so `winapi`
  means everything; `-kernel32/heap` excludes). `THESEUS_TRACE=wm` logs
  window messages.
- `THESEUS_MISSING_ADDRS=path` records jump targets the translator didn't find,
  for feeding back with `--entry-points-file`.
- `THESEUS_CD_LABEL=MOTO_RACER` is set by `run.sh`; `GetVolumeInformationA`
  reports it for drive D:, which we present as a CD-ROM. All drives map to the
  current directory, so the game finds `DATA\` whether it looks on C: or D:.
- `THESEUS_HEADLESS=1` runs without a window (CI). It still has sound: the
  SDL audio subsystem is initialized when the first stream is created, not
  alongside the window.
- `THESEUS_DSOUND_WAV=path` writes everything the DirectSound mixer produces
  to a .wav, which is how sound effects get checked without listening. CD
  audio is a separate stream and does not appear in it.
- `THESEUS_DUMP_FRAMES=dir THESEUS_DUMP_EVERY=150` writes every 150th
  presented frame to `dir/frame_NNNN.ppm` (max 100 files), so a headless run
  can be checked visually. `python3 -c` a tiny PPM-to-PNG converter, or open
  the PPMs directly, to look at them.
- `RUST_BACKTRACE=1` for panics inside winapi.

## About the game binary

- `game.EXE`, 1 MB, MSVC 4.2, MFC 4.2 statically linked, linked 1998-07-09
  ("Polygons version 3.22", see `readme.txt` in the install dir). Entry point
  0x4b6420. The retail CD build (`moto.exe`, 1997) is the same program a year
  earlier; addresses below are for `game.EXE`.
- Imports: kernel32, user32, gdi32, advapi32, winmm (timers, CD audio via
  `mciSendCommandA`, joystick, mixer), ddraw (`DirectDrawCreate`,
  `DirectDrawEnumerateA`), dsound (`DirectSoundCreate`), dplayx (ordinals 1
  and 2: `DirectPlayCreate`, `DirectPlayEnumerateA`), comdlg32, winspool,
  comctl32. Direct3D is reached through `IDirectDraw::QueryInterface`, not an
  import.
- GUIDs present in the binary: IDirectDraw, IDirectDraw2, IDirectDrawSurface,
  IDirectDrawSurface2, IDirectDrawPalette, IDirectDrawClipper, IDirect3D,
  IDirect3DTexture, IDirectSound, IDirectSoundBuffer, IDirectSound3DBuffer,
  IDirectPlay, IDirectPlay2, IDirectPlay2A.
- Command-line flags (strings in the exe list them with help text): `-windowed`,
  `-fullscreen`, `-NoD3D`, `-D3D`, `-NoSound`, `-NoMMX`, `-NoCpuDetect`,
  `-NoPal256`, `-Pal16`, `-Alpha`, `-FrameRateMax<n>`, `-DoRealLock`,
  `-us/-fr/-gr/-it/-sp/-sw`, `-NbComp<n>`, `-J<n>`, `-SnapShot`. The 3.22
  build's flags are capitalized as shown and matched case-sensitively.
  `motoracer.ini` holds the flags GOG's launcher passes for Direct3D on
  Windows; we don't use them. The game has a software renderer, so **Direct3D
  is not needed**: run with `-NoD3D`, and `QueryInterface(IID_IDirect3D)` is
  refused.
- Data: `data\*.BKF` archives, `data\ile0N\*.TRK` tracks, `data\*.BPT` text
  configs, `data\config.txt` (`-us`, the language). The game reads them with
  CreateFileA/ReadFile/SetFilePointer/GetFileSize relative to the current
  directory (macOS is case-insensitive, which papers over `DATA` vs `data`).
- Uses the FPU heavily and optionally MMX (`-noMMX` disables; `tc/src/codegen/mmx.rs`
  covers only a few MMX instructions, so translate-time failures there are
  possible if the MMX path is reached; the CPU detection uses `cpuid`, which
  codegen treats as unsupported, see `misc.rs` in codegen).

## How the pieces work (for someone new to Theseus)

1. `tc` loads the PE, discovers code from the entry point plus scans
   (`--scan-immediates`, `--scan-memory`), and emits one Rust function per basic
   block. Every imported function `dll!Func` becomes a call to
   `winapi::dll::Func_stdcall`, so **an import that winapi lacks is a compile
   error** in `out/moto`. Add the function (see below) rather than editing the
   generated code.
2. COM interfaces (DirectDraw etc.) are vtables of function pointers. tc reserves
   addresses for every entry listed in `winapi::ddraw::VTABLES` (and dsound,
   dinput) and writes them into `init()` in `generated.rs`. **Adding a new COM
   interface therefore requires re-running `translate.sh`.**
3. At runtime, `runtime::Context::indirect(addr)` maps an x86 address to a block
   function. A jump to an address no block covers panics with
   "missing addr"; the fix is usually a tc scanning option or
   `--entry-point`, see `out/chillin/translate.sh` for examples.
4. **Self-modifying code.** The game's texture-mapping inner loops (around
   0x4a4e24, 0x4a4f8f, 0x4a5b0b) contain `12345678h`/`12h` placeholder
   constants that the game overwrites with real addresses and step values
   before running them. Static translation would bake in the placeholders, so
   `translate.sh` passes `--patched-code start..end` for those ranges: tc then
   emits `ctx.memory.read::<u32>(<address of the constant bytes>)` instead of
   the constant for immediates and displacements there. To find more such
   loops, grep the generated code's disassembly comments for `12345678h`.

### Adding a Windows API function

Put it in the matching module under `win32/winapi/src/<dll>/` and mark it
`#[win32_derive::dllexport]`. The macro generates `Name_stdcall`, which pops
exactly one dword per declared parameter, so **the parameter count must match
the real API** or the stack is corrupted. Parameter types implement
`FromABIParam` (`u32`, `i32`, `bool`, `Ptr<T>`, `HANDLE`, enums via
`win32_derive::ABIEnum`, flags via `win32flags!`). Return types implement
`Into<ABIReturn>` (`u32`, `i32`, `bool`, `()`, `HANDLE`, ...).

Prototypes can be generated from Microsoft's metadata with `win32/extract`
(needs `Windows.Win32.winmd`, see its README), which avoids guessing parameter
lists.

Conventions: `stub!(value)` logs a warning and returns `value`; `todo!()` for
things that should never be reached. Functions that call back into x86
(`EnumDisplayModes`, `DirectDrawEnumerateA`, `cbt_create_wnd`) allocate any
structures on `kernel32::lock().process_heap`, drop the lock, then
`ctx.call32_x86(ctx.indirect(addr), args)` and read `ctx.cpu.regs.eax`.

### Where things are

- `win32/winapi/src/user32/`: one host-backed window is modelled
  (`state().window`), with per-window `wndproc`/style/user data so
  `SetWindowLong(GWL_WNDPROC)` subclassing works. Window classes are a list
  keyed by name (`wndclasses`). Dialogs and their controls are a separate,
  lighter table (`state().dialog_windows`, `dialog.rs`) with no window
  procedure or on-screen presence of their own — `GetDlgItem` looks them up
  by id. `hook.rs` implements the WH_CBT hook MFC needs to attach its `CWnd`
  objects (both `CreateWindowExA` and `CreateDialogIndirectParamA` deliver
  it).
- `win32/winapi/src/ddraw/`: `ddraw1.rs` is IDirectDraw/IDirectDrawSurface
  (DirectX 1), `ddraw7.rs` is the DX7 flavour. Surfaces are software buffers
  blitted to the host window.
- `win32/winapi/src/dsound.rs`: DirectSound with a software mixer feeding
  `host`. Sound effects need nothing moto-specific from it.
- `win32/winapi/src/winmm/mci.rs`: the `cdaudio` MCI device, backed by the
  ripped tracks (see "CD music" below).
- `host/`: SDL3 (native) or web backend.

## What the game does at startup (as observed)

1. MFC init: registry reads of its own key (see `moto.reg`), locale, menus.
   `RegOpenKeyExA(HKLM\SOFTWARE\DelphineSoft\MotoRacer\CurrentVersion\Moto)`;
   `Version`, `InstallType`, `PId` must be DWORDs and `PId` must equal the hash
   of `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\ProductId`
   (`h = (h*2) ^ c`; the routine was at 0x42e530 in the CD build), else
   "PROGRAM INCORRECTLY INSTALLED". GOG's installer must write these keys on
   Windows; `moto.reg` does it here.
2. Creates its main window (class registered through MFC, subclassed via the
   WH_CBT hook), then a modeless dialog from a resource template
   (`CreateDialogIndirectParamA`, control id 1005) — created for real since
   2026-09-09 (see "Where things are" above), with HCBT_CREATEWND delivered
   so MFC's `CWnd` attaches to it.
3. `DirectDrawEnumerateA`, `DirectDrawCreate`, `QueryInterface(IID_IDirectDraw2)`,
   `EnumDisplayModes`, `GetCaps`, `GetDisplayMode` (must say 16 bpp, else
   "16 bits screen mode requiered !"), Release, then `DirectDrawCreate` again,
   `SetCooperativeLevel(EXCLUSIVE|FULLSCREEN)`, `SetDisplayMode(640,480,16)`,
   `CreateSurface` x2, `QueryInterface(IID_IDirectDrawSurface2)`,
   `GetSurfaceDesc`/`GetPixelFormat` (must report 16 bpp).
4. CD audio: it scans the drives for its disc (see "CD music" below), opens
   the `cdaudio` MCI device and polls it from a one-second `SetTimer`.
   Anything that goes wrong here it writes to `DATA\delphine.err`, which is
   worth reading — it names the call that failed. `-nosound` skips
   DirectSound; there is no reason to pass it now.
5. Loads `DATA\*.BPT` and `*.BKF`. Its loader uses C++ exceptions (`throw int`)
   as part of normal control flow, so SEH had to work (`kernel32/seh.rs`).
6. Updating the loading dialog no longer throws: `GetDlgItem` now finds the
   real control (previously this threw `CNotSupportedException`, caught by
   MFC's `CWnd::WindowProc` and reported with an empty message box — harmless
   here, but the same exception recurred every frame once racing starts,
   since the in-race HUD updates through a dialog control too; see Known
   gaps history below).
7. Menu pages load (`MENU.BKF`, `MENUUS.BKF`, `PAGES.BKF`), then the 3D
   intro runs (Delphine logo; texture mappers are self-modifying code, see
   below) and the title screen appears; the game then idles pumping
   `PeekMessageA`, waiting for a key.

## CD music

The soundtrack is on the disc as audio tracks 2..13, which the GOG installer
ships as `02.wav`..`13.wav` next to `game.EXE`. `winmm/mci.rs` presents those
as the disc: track NN is `NN.wav`, and a track with no file (track 1, the data
track) is reported as non-audio, so the table of contents the game walks is the
one it expects. Playback streams a track into its own host audio stream and is
fed by `winmm::pump()`, called wherever `dsound::pump` is.

Two things about the game's side are worth knowing before changing any of it:

- **It hunts for its CD by drive letter.** The scan at 0x4b1460 in `game.EXE`
  (the "Class CD:" object) walks the drives three times over. On the first
  pass it wants a drive whose `GetDriveTypeA` is `DRIVE_FIXED` — GOG patched
  this build for a hard-disk install — and whose volume label starts with
  `moto_rac`; ours is `THESEUS`, so that pass finds nothing. On the second
  pass it settles for any drive whose MCI device opens, which is how we get
  in. Reporting the label on a fixed drive would let the first pass succeed,
  but nothing needs it.
- **It decides a track has ended by polling.** A one-second `SetTimer` asks
  `MCI_STATUS_MODE` whether the disc is still playing. So `MCI_MODE_PLAY` has
  to last exactly as long as the audio does — hence position being measured
  from what the audio device has consumed rather than what has been handed to
  it. Report a track as over early and the music restarts mid-phrase.

## Known gaps, in likely order of mattering

0. **Multiple real (host-backed) windows.** user32 still models exactly one
   such window (`user32::State::window`); a second `CreateWindowEx` still
   replaces the first (warning logged). Dialogs are no longer part of this
   gap (see "Where things are" above): `CreateDialogIndirectParamA` parses
   the DLGTEMPLATE and registers a dialog plus one entry per child control,
   and `GetDlgItem` finds them by id. What's still missing there: the
   controls have no real class/rect info parsed out, no window procedure, and
   nothing draws them — fine for code that only checks a control *exists* (as
   moto's HUD update does), not for anything that needs one rendered or
   sent a real message.
1. **`WM_CREATE`/`WM_NCCREATE`** are not sent on window creation; MFC does some
   setup in `OnCreate`. See the TODO in `CreateWindowExA`.
2. **x87 coverage.** `tc/src/codegen/fpu.rs` implements the common instructions;
   an unimplemented one compiles to a `panic!("X not implemented")` in the
   generated code and is hit only when executed. Add it, re-translate.
3. **MMX/cpuid.** `-noCpuDetect -noMMX` avoid both paths; `cpuid` compiles to a
   runtime `todo!()`. The MMX blitters could be enabled later by finishing
   `codegen/mmx.rs`.
4. **Rendering correctness.** Surfaces are 16-bit RGB565 buffers; `Blt` handles
   copies, color keys and color fills; stretching, mirroring and `DDBLTFX`
   effects are not implemented. Palettes only for 8-bit surfaces.
5. **Input.** The game reads keys via window messages and `GetKeyState` (no
   DirectInput import). Joystick reports no devices.
6. **Music volume.** The game applies `MasterVolume`, `CDVolume` and
   `WaveVolume` from its config to the system mixer, once at startup —
   there is no in-game slider behind it. `winmm/mixer.rs` reports no mixer
   device, which the game handles, and everything plays at full volume.
   Presenting a mixer was tried and reverted: the config has no
   `MasterVolume`, so the game reads 0 and sets the master line to silence,
   muting itself. Anything implementing this later must leave the speakers
   (`DST_SPEAKERS`) line out — it is the host's volume, not the game's.
7. **`IDirectSound3DBuffer`** (GUID present in the exe) does not exist;
   `QueryInterface` fails and the game falls back to plain stereo panning,
   which is what it does on hardware without 3D sound.
8. **IDirect3D**: keep returning `E_NOINTERFACE` and run with `-noD3D`; the
   game has a software renderer.
9. **DirectPlay**: stubbed to fail; multiplayer is out of scope.
10. **Exceptions and the Rust stack.** A caught C++ exception leaves a few Rust
    frames behind for good (see `kernel32/seh.rs`); thousands of exceptions
    would overflow the stack. If that happens, run the program on a thread
    with a large stack, or rework the dispatch so handlers are entered by
    returning a continuation rather than by a nested `call32_x86`.

  new patched-code ranges and a new catch-continuation address; intro and
  title screen render as before (~47 fps headless, this build limits the
  frame rate). History rebased so generic Theseus commits come first; the
  CD-based history survives as branch `lu-moto-racer-cd`.
- 2026-09-09 (later): First input testing found three bugs blocking an actual
  race, all fixed:
  - `fprem` (x87 float modulo, used constantly by the angle math a race
    needs) computed the right value but never updated the FPU status word,
    so the `fnstsw`/`sahf`/`jp` retry loop MSVC emits around it could spin
    forever whenever an earlier comparison happened to leave C2 set — hung
    the game as soon as a race started. Added `FPU::prem()`, which reports
    C2 clear and the quotient's bits in C0/C1/C3 (Intel SDM Vol. 1 8.3.5).
  - `CreateDialogIndirectParamA`/`GetDlgItem` were fully stubbed, and the
    in-race HUD updates through a real dialog control (not a sprite) every
    frame, so it threw `CNotSupportedException` every frame — the catching
    handler aborted the rest of that frame's draw, leaving only the sky/water
    background on screen (a persistent, not transient, bug: it lasted the
    whole race). Added dialog/dialog-control window tracking — see "Where
    things are" and Known gaps above.
  - Separately, `Surface::flip` only refreshed the on-screen texture when the
    front surface had a palette (`ddraw.rs`) — irrelevant for this 16bpp
    (RGB565) game, so the window never updated past its first frame while the
    guest-memory back buffer (and `THESEUS_DUMP_FRAMES` dumps, which read it
    directly) kept rendering correctly underneath. This made the bug
    invisible to headless testing and produced the confusing symptom of the
    same build looking perfect in dumped frames and broken on screen at the
    same moment. Fixed to refresh unconditionally (same fix as `00b5e95e` on
    branch `lu-mm2`, ported here). Result: a full race — menus, track/bike
    select, racing, HUD, going off-track, GAME OVER — renders and plays
    correctly.
- 2026-09-09 (later still): Sound. DirectSound turned out to need nothing:
  running without `-nosound` already mixed the game's effects correctly, once
  there was a device to play them on — SDL's audio subsystem was initialized
  only alongside a window, so a headless run had none. Music needed the rest:
  `SetTimer`/`KillTimer` (stubbed to fail, so the game logged "Can't install
  timer for CD control") and a real `mciSendCommandA` (stubbed to report
  success, so the game read back its own "not ready" default and gave up with
  "device not ready in getStatus()"). Both are in the general Theseus code,
  not moto-specific. Result: the intro jingle, menu music and race music play
  from the ripped tracks, changing with the screen, alongside engine and
  effect sounds.

  Two things about the game's own behaviour surfaced while testing this, both
  the same on hardware and neither worth trying to "fix": its 1-second timer
  restarts a finished track exactly once, because `playTrack` clears the
  loop flag it just acted on (0x4b1ad2), so music stops until the next screen
  change; and a track that ends is not otherwise noticed. With 2-3 minute
  tracks and a screen change every minute or so, neither shows. Shortening
  the `NN.wav` files to a few seconds each makes both obvious in a minute,
  which is the way to exercise the track-end paths.
